# Console federated access

The Console accepts external OpenID Connect identities through OAuth 2.0 authorization code with S256 PKCE. Each installation chooses its identity provider, issuer, client registration and credentials. No provider is bundled, selected by default or required by Redcode. Plain OAuth2 without an OIDC identity contract is not supported: an access token alone does not identify a user.

## Configure your identity provider

Configure providers in the Console UI. New installations show an optional authentication step after creating the first account. Existing installations use the scoped authentication settings in the side menu:

- **Infrastructure → Global authentication**: infrastructure admins set the public Console URL and providers shared by all scopes.
- **Infrastructure → Owner authentication**: owner admins configure providers for their infrastructure members.
- **Organization → Authentication settings**: organization owners/admins configure providers for their organization.

An organization role never grants infrastructure administration. Owner users and organization members cannot edit these settings. Older installations without an infrastructure owner use the existing **Claim infrastructure** screen with the local setup code.

Save the public Console URL first, then add the provider name, issuer URL, client ID, token authentication method and client secret if required. The authorization, token, UserInfo and JWKS endpoints are discovered from the issuer's OIDC metadata. No company issuer or realm is hardcoded. **Test** verifies discovery; a complete sign-in verifies client credentials and callback registration. Providers are disabled by default in the add dialog. Enable them when ready.

Register a client through your provider's administration tools. Configure:

- Authorization code grant, response type `code`, with S256 PKCE.
- Scopes `openid email profile`.
- The exact redirect URI `<publicURL>/api/console/federation/callback`.
- A token endpoint authentication method matching the method selected in the Console.

For example, the local template's callback is `http://127.0.0.1:35556/api/console/federation/callback`. A production installation might use `https://console.example.org/api/console/federation/callback`. These are examples of the Redcode callback, not endpoints for a required identity service. Use the actual Console origin you control.

Enter client secrets in the password field. The Console persists them in its existing credential store, separately from provider metadata. They are never returned by settings or provider-list APIs, and the edit field is always empty. Leave it empty to retain an existing secret; enter a new value to replace it. Changing issuer or client ID for a confidential client requires a new secret. Protect the Console database and its backups as credential material.

Production browser access requires an HTTPS public Console origin. Loopback HTTP is accepted for local development. Client registration and provider admission rules are managed by the installation's identity administrator.

## Start

1. Run `redcode console serve --port 35556`. From repository source, use `bun run dev console serve --port 35556`.
2. Complete local onboarding and its optional authentication step, or open the settings listed above.
3. Open the exact saved public Console URL. `localhost` and `127.0.0.1` are different browser origins; the callback and origin check must agree with the registered URL.
4. Share the **Sign-in link** shown in settings. The default login page lists global providers. Organization and infrastructure links include their context and list their specific providers plus inherited global providers.

The Console binds to loopback. A remote HTTPS URL requires a correctly configured reverse proxy/tunnel to that listener. Use a stable port. Authentication settings are stored in the Console database and changes apply immediately without a server restart or a configuration file. Deleting or changing a provider invalidates its pending sign-in attempts; changing the public URL invalidates all pending attempts. Already issued local sessions remain valid.

Confidential clients support `client_secret_basic` and `client_secret_post`. Public clients select `none` and leave the secret empty. URLs require HTTPS, except loopback HTTP. IDs are generated by the Console. Administration changes are audited without secrets.

## Account admission

Bootstrap still requires the local setup code. No IdP user can turn an unconfigured Console into their own organization.

For an existing account, sign in locally, open **Account**, and select **Link** for the desired provider. The local session must have been created within five minutes, and remain valid when the callback arrives. The IdP is asked for a fresh login. Matching email never links or takes over an account; identity is the exact discovered issuer plus stable OIDC `sub`. The same subject in two realms is independent.

For a new account, a Console administrator creates an invitation for the user's email. Choose **Join with** the provider and enter the invitation code. The provider must return a verified, matching email. The invitation is checked again and consumed transactionally when the account, membership and identity are created. The invited role is preserved. IdP `role`, `realm`, `org_role`, groups and domain claims do not grant local roles.

Subsequent sign-in uses the linked identity and existing memberships. An invitation to another organization can be accepted while signed in. Membership and key revocation continue to use Console authorization.

Specific organization/owner providers check membership in that scope again at callback. An organization invitation can admit someone to its organization's provider; it never grants owner access. Owner members must already have infrastructure membership. Global provider inheritance does not create memberships or elevate roles. Account settings list providers applicable to the signed-in account so it can link its identities.

## Sessions and limits

Attempts persist in the Console database for ten minutes, including PKCE verifier and nonce. State and browser-cookie bindings are hashed. A valid callback consumes the attempt before code exchange. The browser cookie is HttpOnly/SameSite=Lax, Secure on HTTPS. Origin checks protect flow initiation and session exchange. Issuer, audience, nonce, expiration, RSA/JWKS signature and UserInfo subject are validated by `oauth4webapi`; provider fetches time out and reject redirects. The JWT issuer is discovered and pinned to the configured issuer.

Provider access/refresh tokens are discarded server-side after identity verification. The callback redirects without tokens in the URL, setting a short-lived HttpOnly handoff cookie. The same-origin browser POST consumes and rotates that local session once; the final Console token uses the existing sessionStorage flow. Local Console sessions expire after seven days, with immediate local logout/revocation. Expired attempts are removed on subsequent sign-in initiation.

This is federated login, not continuous IdP session introspection or global SSO logout. Disabling an IdP account does not revoke an already-issued local Console session until local revocation/expiry. Directory synchronization, SCIM and role mapping are separate integrations. Federation does not authorize the agent server, workers, filesystem or shell endpoints: the Console remains a separate listener and authorization domain.

Invited federated accounts have no local password; they sign in through their provider. Password and account-deletion forms requiring a local password are hidden for them. Federated reauthentication for account deletion and unlinking identities are not implemented. Existing accounts retain their local password as a fallback; local login has not been disabled.

## Validation

From `packages/server`, run `bun test test/console.test.ts test/console-federation.test.ts`. Federation tests use a disposable local HTTP IdP with real signed RSA tokens, code exchange, PKCE, JWKS and UserInfo. They cover successful linking/login, state/browser binding, token-claim and signature failures, invitation admission, realm separation, one-use handoff, logout, durable attempts across Console recreation and upgrading an existing Console database. Run an integration check against your configured identity provider before activating it for users.

The optional production-page browser test uses Playwright in a separate Node process. Set `REDCODE_TEST_BROWSER` to an installed Chromium/Edge executable and optionally `REDCODE_TEST_NODE` to Node's executable, then run `bun test test/console-federation.test.ts -t 'production Console browser'`. It exercises the real embedded DS page and Console API through linking and subsequent federated login, without touching the running Console or its database. `REDCODE_TEST_SCREENSHOT` optionally records the Account page.
