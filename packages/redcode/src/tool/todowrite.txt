Track multi-step work as concrete tasks. Enumerate EVERY item in a multi-part user request, including verification, then start real work in the same turn. Skip this tool for simple or informational requests.

Each call creates or updates the supplied tasks. Omitted tasks are preserved. Send {"todos": []} to read the current list, the five latest user request IDs and up to twenty recent tool results with callID, messageID and success status. Use the id and current revision returned by the tool for subsequent updates; an exact content match supports older callers. Do not invent IDs or rename a task by dropping it and creating another.

Shapes:
- Create: {"content":"<task>","status":"pending","priority":"high","requirement":"<quote from the user request>","criterion":"<observable result>"}. Content and priority are required only here. Users may write in any language: a requirement that quotes the request links that message; a paraphrase or translation is never refused, it is linked to the latest user request, kept as the criterion, and the output says so.
- Update: {"id":"<id>","revision":<current revision>,"status":"in_progress"} plus only the fields that change; content and priority stay as stored.
- Complete: {"id":"<id>","revision":<current revision>,"status":"completed","evidence":{"callID":"<successful result>","messageID":"<its message>","explanation":"<how it meets criterion>"}}. Evidence may be omitted only when a verification result exists: the newest successful bash/shell check, design_preview or design_export after the request and after the last edit is recorded automatically and the output says which (quoting a shell check's command). A shell check is recorded for you only when the task has a criterion or reason; otherwise cite the verifying command with an explanation. Edits and reads are never selected for you.

States:
- pending: actionable work not yet started.
- in_progress: the task being executed. Keep one active task; the next pending task is promoted automatically.
- blocked: a concrete obstacle prevents progress. Supply reason, preserve the requirement and execute independent tasks. Unblock by updating to pending or in_progress when the obstacle is resolved.
- completed: the requested result has been implemented and verified. A plan or promise is not completion.
- cancelled: work was removed from the authorized scope. Supply the scope-change reason. Never cancel just to finish the conversation, hide a failure or avoid a blocked item.

Update progress when it changes. Partial updates and empty lists never clear unfinished work. Conflicting stale revisions are rejected; read the current list before retrying. A blocked task is not complete: state what remains, why it cannot proceed and the next action.

Verification protocol: after the last edit run the check that proves the task (tests, build, a command that exercises the change); that result is the evidence. Cite its callID with an explanation, or omit evidence and let the tool select it. An edit is not evidence that it works. Investigation tasks (explore, find, explain) may cite the read, grep or other result that answers them, with an explanation. Only a later edit (write, edit, apply_patch, design_edit, design_generate, design_asset) to the verified files invalidates evidence; then run the check again before completing. Commands run after the proof never invalidate it, so a formatter, codegen or `sed -i` run through bash after the tests is your responsibility: run the tests again after it. A cited result that is unknown, failed, older than the request, bookkeeping or stale is refused with that reason and no other result is substituted; the refusal lists the recent callIDs, tools and messageIDs inline, so act on it instead of resending the same completion. After two refused completion attempts in a turn the task is blocked with that reason. Tool provenance is checked by the runtime; you must still judge relevance and coverage honestly.

To cancel tracked work, include scopeChange: {"messageID":"<user request ID>","quote":"<the instruction removing the requirement>"} and a concrete reason; a quote that matches no message is linked to the latest user request instead of being refused, but the reason is always required. Technical obstacles belong in blocked with their concrete cause. A continuation budget pause preserves actionable tasks; resume them when the user requests continuation.
